    Integrating Video Playback into a Camera2 Preview

## 🔧 TroubleshootingAndroid’s Camera2 API provides a low‑level interface for camera capture, and you can overlay or blend a stored video with the live camera feed by managing multiple view surfaces. In practice this means running the camera preview and video decoder on separate surfaces (often two TextureViews or one TextureView/SurfaceView for each) and composing them in the UI. Alternatively, for advanced use you can use OpenGL (e.g. via Grafika’s examples) to render both streams into a single output surface. Below we outline the key steps and considerations, citing official docs and community examples.

    • OpenGL compositing (advanced): If you need to blend pixel data (e.g. picture-in-picture, custom effects, or recording both streams into one video), a common approach is to render both textures in an OpenGL ES shader. Google’s Grafika sample demonstrates this: its RecordFBOActivity shows how to draw camera (OES) texture and video texture into a single frame[9]. Essentially you decode the video with MediaPlayer into a GL texture and capture camera preview frames into another texture, then render both to an output surface. This requires significant OpenGL coding (shaders, EGL contexts) but gives maximum flexibility (mixing, filters, recording). The Grafika project on GitHub is a key reference for such pipelines[9].
    • Camera2 multi-target (unlikely direct): Camera2 can deliver its output to multiple surfaces (e.g. a preview view and an ImageReader for analysis)[10], but it cannot directly take a video file as an “input” to output through the camera device. There is no built-in Camera2 API to inject a video stream into the camera sensor’s pipeline. Instead, treat the video and camera as separate pipelines at the application level (as above).
State Management (Pause/Resume/Switching)
Handle activity/fragment lifecycle properly:
    • Camera lifecycle: On onResume(), reopen the camera and start preview; on onPause(), close the camera and stop the background thread. (Example: see Camera2BasicFragment’s onResume()/onPause() handling.) This ensures the camera is released when your app is backgrounded.
    • MediaPlayer/ExoPlayer lifecycle: Likewise, pause or release the player on onPause(). For example:
    • @Override protected void onPause() {
    super.onPause();
    if (mediaPlayer != null) {
        mediaPlayer.pause();
    }
    closeCamera();
}
@Override protected void onResume() {
    super.onResume();
    if (mediaPlayer != null) {
        mediaPlayer.start();
    }
    openCamera();
}
    • Toggling modes: Keep state (e.g. a boolean isVideoMode). When switching, start/pause the appropriate stream. For example, if switching from camera to video: pause or stop preview, then call mediaPlayer.start(). UI-wise, you might enable/disable buttons accordingly.
Careful: if overlaying both, coordinate their rendering (don’t let both play on top of each other unless desired). Also handle audio focus if video has sound.

SurfaceView vs TextureView
As noted, use SurfaceView for best performance and low latency (ideal if you do full-screen video or high-res camera preview)[3]. However, SurfaceView is a separate window buffer and doesn’t support view transformations or easy layering. TextureView is a regular View, supports rotation/alpha, and can be moved in the View hierarchy, but uses more GPU/memory.
    • Use TextureView (or PreviewView from CameraX) if you need to easily overlay or animate the preview/video. (As one answer on StackOverflow suggested, “using TextureView for your camera preview” if you need to layer videos above it[11].)
    • Use SurfaceView (or VideoView) if smooth, efficient rendering is needed and you can keep it static.
Jetpack’s PlayerView/StyledPlayerView (ExoPlayer) can use either mode via app:surface_type. In Compose, you’d wrap Android Views (see [37]) or use dedicated Compose Video support.

Blending or Alternatives
    • Simple Overlay: Place a transparent VideoView/TextureView atop the camera preview (for example, showing an animation or UI).
    • Picture-in-Picture / Facecam style: Resize the video view to a corner on top of the camera feed.
    • Chroma Key / Filters: If more complex, decode video frames and camera frames (via ImageReader) and merge in CPU or GPU. This can be done with ImageAnalysis (CameraX) or ImageReader (Camera2) plus MediaCodec to mix streams, but requires extensive processing code.
    • Recording both streams: As one SO answer notes, to record camera + video into a single file you’d likely use OpenGL (e.g. Grafika’s approach) or capture the UI with MediaProjection (screen record)[9]. There’s no simple built-in API to “record both layers at once” aside from screen capture.
UI Considerations
    • PreviewView (CameraX): Though the question is about Camera2, consider that Android’s newer PreviewView (from CameraX) automatically handles many preview issues. It also offers overlay capabilities (see Implement a preview). You could use a PreviewView for camera and still overlay a video player view on top.
    • Controls: Provide buttons or toggles to start/stop video, switch cameras, toggle overlays, etc. Place them in layouts above the video layer.
    • Surface lifecycle: Remember a SurfaceView’s surface is tied to view visibility, whereas a TextureView’s surface is tied to window attachment[12]. On Android 14+, SurfaceView lifecycle can be adjusted, but if manually managing surfaces, be aware that a SurfaceView’s surface may briefly disappear during view transitions.
    • Performance: Playing a video and camera simultaneously can be CPU/GPU intensive. Keep resolutions reasonable, and consider using SurfaceView for the video if no overlay is needed (since it’s more efficient)[3].
Limitations and Workarounds
    • Not a “virtual camera”: Android does not let you feed a video file into the camera sensor’s pipeline as if it were live camera data. Workarounds involve capturing the camera data via ImageReader and blending with video frames in software or GLES, then optionally encoding with MediaCodec.
    • Z-order of Views: If you use a VideoView (which uses SurfaceView), be careful: SurfaceView layers are ordered by their android:elevation or Z. Often VideoView will float to the top window layer, obscuring anything behind it. The FrameLayout layering trick only works cleanly when both are TextureViews or using PlayerViews with Texture.
    • Background operation: Camera2 requires a foreground context on modern Android; background services can’t access camera. Make sure your app is in foreground or use a foreground service if persistent capture is needed.
